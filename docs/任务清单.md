## 长期 Agent 引擎路线（触发式）

### 已确认决策

- **短期继续使用 PI**：只跟进选定的稳定版本和安全修复，不追逐每个上游版本。
- **fork 保持薄**：只保留少量、可单独测试、能按行为重放的补丁；不把深度魔改继续堆入 PI fork。
- **不做深 fork**：它既承受高频上游冲突，又无法获得真正独立的架构边界，长期成本最高。
- **深度定制进入自有引擎**：E1 触发后，新的执行循环、事件协议、会话策略和编排能力进入 `NativeAgentEngine`；触发前不为预想中的定制提前建设第二套运行时。

### Phase E0：建立 AgentEngine 防腐层

**目标：** 服务端、主 Agent 和子 Agent 不再直接依赖 PI 的 `AgentSession`、`ModelRuntime` 和 `SessionManager`。

E0-a 最小引擎契约已完成并归档；本节只跟踪尚未完成的 E0-b。

**E0-b：** 将剩余 PI 接入收口到 `PiAgentEngine`，完成主会话、子 Agent、设置页和 SSE 的适配迁移。已完成并归档。

**usage 契约边界：**

- `ProviderUsage` 表示单次 provider 请求返回的原始 input、output 和 cache 计量。
- `ContextUsageSnapshot` 表示当前上下文占用及 `exact`、`mixed`、`estimated` 来源。
- `CostLedger` 只消费 `ProviderUsage` 与 `PriceCatalog` 生成金额和预算记录，不扫描会话文件，也不重新计算 Token。
- `PiAgentEngine` 与未来的 `NativeAgentEngine` 必须提供相同契约，不能各自定义一套 usage 语义。

**E0-b 完成标准（已满足）：**

- PI SDK 的直接 import 只允许出现在适配器和 SDK 合约测试中，并有结构门禁。

## Agent Profile 与工具呈现路线（dsh 借鉴）

当前项目已有 `PermissionMode`，但它只负责授权；dsh 的 preset 和 tool presentation 还没有对应的独立抽象。新增能力必须保持三层分离：

```text
AgentProfile       → 当前 Agent 拥有哪些能力和提示词
ToolPresentation   → 模型以 native、ptc 或 both 方式调用能力
PermissionMode     → 具体调用是否允许执行
```

- [ ] **AP-15 [P1][能力组件架构] Bootstrap Kernel、Required Component 与 Optional Component 分层**
  - 术语统一使用“能力组件（Capability Component）”；“组件”表示可安装、可替换、可治理的运行时能力，“单元”只保留给内部部署/测试粒度，不作为产品架构名称。
  - **最小实现（第一阶段）**只做 manifest/schema、catalog、信任、启用/停用、健康状态、generation、依赖检查、权限转发和生命周期审计；复用现有 ToolRegistry、ToolPool、Profile、MCP trust-store、Permission/Security 和 UI 注册入口，不引入市场、热更新或通用动态代码执行。
  - **当前进度（2026-08-27）**：前四阶段已完成。第一阶段交付最小管理闭环；第二阶段交付 Required Component 隔离预检、高风险批准、契约校验、串行原子切换、有界验证、持久化/健康回滚、session generation 固定和引用归零释放；第三阶段新增不可变 runtime provider binding，session lease 同时解析 provider ID 与真实实现，已将 `ToolPresentation` 作为首个真实执行插槽接入 Agent 工具装配；第四阶段定义项目自有 `ModelRouterSession/ModelRouterProvider` 窄契约，将 PI provider runtime、模型目录、认证状态、刷新和同步绑定到 session lease 的 generation，主 Agent、子 Agent、设置路由和模型同步均通过该契约访问。已绑定 group 禁止切换到 manifest-only 候选且强制 post-switch verify；重启时缺少可执行 binding 会 fail-closed 留在内置 provider。旧 session 继续使用旧呈现和模型路由实现，新 session 使用新实现；替换失败会回滚，旧 lease 在引用归零后才释放。permission、安全 parser、trace 和 abort 的 canonical `execute` 包装仍由宿主强制持有。其他 Required 能力要逐项定义宿主接口后才能接入 binding，不因 catalog 中存在 manifest 而宣称已可执行替换；Creator 管理 Profile 与通用动态组件装载仍按后续阶段推进。
  - `Bootstrap Kernel` 定义最小宿主契约：能力发现/信任、契约校验、权限与 sandbox 转发、资源上限、事件 envelope、generation、替换事务和回滚。Kernel 的具体实现也必须作为可替代的 **Required Component** 管理，不把当前宿主实现永久视为不可替换核心。
  - **Required Component（必需组件）**：session store、model router、permission evaluator、security parser、ToolPresentation、MCP host integration 等提供宿主基本闭环的组件。卸载前必须存在满足同一能力契约、版本、权限和资源要求的健康替代者；无替代者时 fail-closed 拒绝卸载。
  - **Optional Component（可选组件）**：独立工具、Skill/Agent 扩展、UI pane、外部 Provider 和单个 MCP server。可选组件可以独立安装、信任、启用、停用和卸载，不得修改 Kernel、全局 ToolRegistry 或其他 session 的能力。
  - MCP 纳入同一组件系统：MCP host/discovery/trust/ToolPool 投影作为 Required Component 能力契约；每个 MCP server、catalog entry 和其工具集作为 Optional Component，统一经过 manifest、信任、权限、安全 parser、资源限制、health 和 generation 治理，保留现有 MCP 配置兼容读取。
  - **可见性契约**：用户界面和宿主可以读取完整 catalog；普通 Agent 只看到当前 Profile 投影后的可用工具和提示词；Creator/管理 Profile 才能调用只读目录与草稿管理工具。组件的启停、信任、替换和卸载始终由用户/宿主确认，不能由普通 Agent 静默触发。
  - 所有组件依赖能力契约和 `replacementGroup`，不得依赖具体实现 ID、绕过 Permission/Security 或改变状态不变量；Profile、ToolPool、ToolPresentation、Execution Contract 和 UI 贡献统一由组件 catalog 生成。
  - Required Component 替换必须先在隔离进程完成静态检查、录制回放、故障矩阵和必要的 shadow 对比，再原子切换到新 generation；旧 session 固定旧 generation，引用归零后才允许 stop/dispose，失败必须回滚。
  - 高风险组件（permission evaluator、security parser、session store、MCP host integration）禁止无用户批准的热替换；没有兼容替代者时返回依赖 Profile、session 和缺失能力的结构化说明。
  - Creator 只能生成和验证 session-scoped 草稿或 Optional Component，不能直接创建/替换 Bootstrap Kernel 或 Required Component；正式安装、信任、启用、停用和 UI 注册必须经过 Component Manager 生命周期流程，并明确用户批准、影响范围和 generation。
  - 集成/跨层测试：component manifest → catalog → ToolPool/Profile projection → permission/security → runtime → MCP/工具执行 → SSE/session JSONL → refresh/replay/fork；覆盖必需组件无替代拒绝、兼容替代切换、MCP server 安装/启停、并发 generation、shadow 差异、崩溃/超时/dispose、可选组件卸载和 Creator 草稿隔离，并纳入 packaged Electron 与 RSS/V8 门禁。
  - **完成标准**：先交付最小组件管理闭环，再扩展替换能力；必需组件始终有健康 provider，替换不影响旧 session 或安全边界，可选组件可独立卸载，MCP 与 Profile、工具目录、UI、运行时事实保持一致。

## 产品定位

**my-code-agent 是安全、可编排、可持续积累能力的桌面工程助手。**

- 首先服务软件工程，不转型为覆盖聊天渠道、日程和生活自动化的泛个人助手。
- 外部 agent 是可选能力提供者，不是固定的“下级”。
- 新能力必须可关闭、可审查、可测试、可回滚。
- “可持续积累”必须同时包含存储与验证，不能只增加记忆数量。

## 能力分层

```text
Tool：执行原子操作
Skill：完成某类任务的方法和流程
Agent：可被调度的角色、上下文与责任边界
Provider：本地模型或外部 agent 的执行来源
```

- 自定义 Agent 可以配置默认 Skill。
- Skill 可以声明所需 Tool，但不能扩张 Agent 的工具权限。
- Provider 不决定上下级关系，只提供能力、模型和成本选项。

## Checkpoint A：学习闭环与价值复核

Task 1～3 完成后先验证是否真的“越用越好用”，不立即进入高成本编排功能。

```text
技能或记忆被使用
  -> 记录来源与结果
  -> 用户保留、修正或禁用
  -> 比较后续命中与失败
  -> 生成技能或记忆草稿
  -> 人工审核后升级
```

**本地验证信号：**

- 技能在至少 3 个不同任务中被重复使用。
- 用户没有立即关闭或大幅重写该技能。
- 启用后产出被保留，测试或手工验收通过。
- 长期记忆至少 3 次正确命中，并减少重复说明。
- 错误记忆能够被发现、修正、追溯和回滚。

**未达到信号：** 暂缓第二阶段，继续修正技能选择、记忆作用域和用户控制，不用增加更多自动化。

## 第二阶段：长生命周期编排（Checkpoint A 通过后）

### Task 4：CostLedger 与预算护栏

**目标：** 在延长子 agent 生命周期前，建立独立成本账本、预算上限和原子中止。

**完成标准：**

- CostLedger 独立于 usage-index。
- CostLedger 只消费统一的 `ProviderUsage` 与 `PriceCatalog`，不扫描 session，也不另建 Token 计算口径。
- 支持 provider/model 输入、输出、cache 价格和计费单位。
- 主 agent 与全部子 agent usage 可以汇总。
- 未知价格明确显示“未知”，不伪造金额。
- 启动前显示成本预估；运行中显示已花费与上限。
- 到达上限后原子中止，不再启动新子任务。

**为什么做：** 长生命周期和多 agent 会放大成本，预算护栏必须先于 continuable 和会议模式。

### Task 5：Continuable subagent

**现状修正：** 只读 fan-out、worker 进程、delegate_tasks、自定义 Agent、并发限制和 usage 汇总已经完成；不再重复建设子 agent MVP。

**目标：** 让现有 one-shot 子 agent 可以继续、恢复和被主 agent 控制。

**完成标准：**

- 支持 `send`、`status`、`abort`、`resume`。
- 子任务描述、事件和结果可以持久化并冷恢复。
- 权限、预算、并发、最大轮数和最大工具调用仍由 supervisor 强制执行。
- 主会话可以查看连续事件、当前状态和最终汇总。
- 父进程退出时能可靠结束或安全保存子进程状态。

### Task 6：会议 / judge panel

**目标：** 在高风险架构决策、评审和方案比较时，允许主 agent 组织多个角色评审并收敛结果。

**依赖：** CostLedger 和 Continuable subagent 完成。

**完成标准：**

- 会议只由用户按需发起，不默认开启。
- 支持不对称模型配置：强主导模型加廉价评审模型。
- 发起前展示预算和参与者，用户确认后运行。
- 评审意见、反驳和最终结论可追溯。
- 达到预算、轮数或时间上限后自动收敛或中止。

## 可穿插的小任务

这些任务与主线依赖较少，可在大任务之间完成，但不应打断 Task 0～3。

- 不改变现有授权语义，只改善可见性和错误恢复。

## 值得验证的方向

这些功能不承诺进入正式架构，每项先通过独立原型回答关键问题。

### V1：ACP 外部 agent provider

只接一个 provider，验证启动、消息、流式事件、中止、进程树清理、权限和 usage。成功后它作为可选 Provider 进入现有编排，不把本项目降为调度外壳。

### V2：Windows 受限执行环境

独立验证普通用户权限、Electron spawn、PowerShell、Git、npm、管道输出、大工作区 ACL 传播、清理和性能。

- 它只补充写侧隔离，不能替代现有命令语义安全和路径治理。
- 必须单独实现 sandbox fail-closed：请求隔离但不可用时执行 `SANDBOX_UNAVAILABLE -> refuse`。
- 验证完成前不接入默认命令链。

### V3：Agent 代码导航工具

基于现有 tsserver 增加 definition、references、hover 等只读工具。先支持 TypeScript/JavaScript；只有实测能减少全文搜索和误读，才扩展更多语言。

### V4：运行态感知与元素定位

分阶段验证：

1. 捕获 dev server stdout/stderr，形成有界日志和错误事件。
2. 通过 Electron CDP 捕获 console error 和 network failure。
3. 用户点击问题元素，将 DOM 快照和批注作为 attachment 发送给 agent。
4. 视觉截图分析只在可用模型下启用，不作为前置条件。

观察默认采用只读；导航、点击和执行操作继续经过权限确认。

### V5：工程型后台任务

只验证测试、构建、索引等工程 job，以及完成通知、查看输出和中止。验证稳定后再讨论定时调度；不扩展成通用生活提醒系统。

### V6：增量事件投影

只为新事件增加统一 envelope、持久化规则和 projection 测试，逐步减少运行时状态与日志不一致。不一次性替换 JSONL、chatStream、SSE 和 AppEventHub。

### V7：最小能力组件接缝

旧 backlog 把扩展系统列为“下一阶段主线”，该优先级已失效。只有出现至少两个真实扩展需要共享安装、生命周期、权限和 UI 注册机制时，才设计最小能力组件 API；优先复用 ToolRegistry、MCP、Skill 和 registerPane，不引入大型运行时框架。MCP server 作为可选能力组件纳入该接缝，MCP host integration 作为必需能力契约治理。

## 观察项

### O1：单窗口单项目多会话并发（④-C）

观察窗口：完成 Task 1～5 后的 4 周或 20 次真实开发任务。

只有出现至少 3 次以下情况才重新立项：用户确实需要在同一工作区维护两个独立主对话，而且多窗口、运行中补充和主 agent 委托都无法替代。

未达到条件时移入“暂不计划”，不长期悬挂。

### O2：定时调度与工作流

只有 V5 工程型后台任务被稳定使用，并出现重复的定时工程任务时再评估。第一版只能调度受权限和预算控制的工程 job。

## 暂不计划

| 功能 | 原因 |
|---|---|
| 泛个人助手和多聊天渠道 | 偏离工程工作台优势，身份、渠道和生活服务均需重新建设 |
| 固定“主人 agent / 下级编码工具”层级 | 外部 agent 应按任务能力参与，不由品牌决定层级 |
| 未经审核自动安装或永久启用技能 | 会固化错误经验，并引入提示注入和供应链风险；只允许生成待审核草稿 |
| 全面事件溯源重构 | 改动面和回归风险过高；采用 V6 渐进收敛 |
| 直接照搬 dsh Windows ACL sandbox | 当前实现是 partial，存在 ACL 残留、传播成本和管道限制；只做 V2 验证 |
| 每包 100% 覆盖率 | 单人项目维护成本过高；继续按安全和风险分配测试密度 |
| 为组件化全面拆包或引入 Cordis | 当前模块边界已可控，没有对应收益 |
| AI 安全分类器自动审批 | 不用概率模型替代现有确定性安全规则；未来最多作为提示信号 |
| 向量索引 / Meilisearch | 当前全文搜索和项目规模未证明需要额外索引基础设施 |
| 自动根据拒绝记录修改系统提示 | 容易把偶然拒绝固化成长期行为；先纳入本地学习信号观察 |
| SSH、社交、移动 VM 功能大包 | 没有明确用户需求；需要时优先以受限 Tool、MCP 或独立扩展验证 |

1. 新规划必须进入本文件，并明确状态、原因、依赖和完成标准。

4. 值得验证的功能先写原型结论，再决定升级、继续观察或放弃。
5. `backlog.md` 和 `agent-capability.md` 后续只保留历史与能力现状，不再各自维护另一套执行顺序。
