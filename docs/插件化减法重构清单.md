# my-code-agent 插件化减法重构清单

> 基线：2026-08-29。状态：待执行。本文替代“所有能力都进入能力组件目录”的推进思路；架构分层仍以 [架构规范](./架构规范.md) 为唯一来源。

## 1. 要解决的问题

当前实现把以下四类对象放入同一个“能力组件”模型：

1. 宿主内部实现：运行时、权限、安全、存储、事件、MCP Host。
2. 可安装产品扩展：Agent 工具包、模型协议适配、可选桌面功能。
3. 外部集成实例：MCP Server、未来的 SSH 或其他连接。
4. 声明式资源：Skill、Profile、Provider、模型和 Memory 条目。

它们的生命周期、所有权、用户操作和安全边界不同。强行共用 `component/package/contribution/productClass/hostSurface/source/kind/generation` 会产生重复目录、伪组件、两跳操作和没有实际收益的替换事务。

本轮目标不是改造出更大的插件框架，而是减少概念、公开入口和运行时分支，使产品体验接近 VS Code 的有序分类，运行时边界采用 DSH 的窄接口与可逆资源释放。

## 2. 目标模型

```text
稳定宿主（普通核心代码，不在用户插件页出现）
├─ 宿主与安全：Electron、preload、权限、PathGuard、锁、事件不变量
├─ 运行时：AgentRuntime、会话、事件投影、ToolPool、MCP Host
└─ 可替换槽位：AgentEngine、ModelRouter、SessionStore（仅内部受控替换）

扩展（用户可安装/停用/卸载）
├─ Agent 工具包
├─ 模型协议适配
└─ 桌面功能扩展

集成（用户配置的外部服务实例）
└─ MCP Server、未来 SSH/数据库/远程服务连接

资源（声明式数据，不作为代码插件）
└─ Skill、Profile、Provider、模型、Memory
```

### 2.1 用户界面

用户只应看到两个管理面：

| 管理面 | 展示对象 | 直接操作 | 不展示的对象 |
|---|---|---|---|
| 扩展 | 可安装的产品功能 | 安装、启用、停用、卸载、查看权限和版本 | 运行时、权限、安全、存储、MCP Host |
| 集成 | 外部服务连接实例 | 新增、编辑、信任、连接、停用、删除、查看工具/健康 | MCP 工具的内部动态注册、连接池、信任存储实现 |

内部核心只在“诊断”显示版本、健康和故障证据，不提供伪卸载、伪替换或与扩展混排的入口。

### 2.2 运行时

- 普通核心模块保持普通 TypeScript 模块，不要求 manifest、generation 或 lifecycle manager。
- 真正可安装代码只使用一种 `ExtensionManifest` 和一种 activate/dispose 协议。
- MCP Server 是 Integration 实例：配置创建 client 实例，client 贡献工具；它不是应用扩展包，也不把每个工具登记成扩展。
- Skill、Profile、Provider、Memory 都是受校验的数据资源；可启停不等于可执行插件。
- 只有 AgentEngine、ModelRouter、SessionStore 等存在多个成熟实现且影响会话一致性的槽位，保留内部受控切换。不要将此机制抽象成面向所有模块的通用组件管理器。

## 3. 设计约束

1. 一个对象只归属于“核心、扩展、集成、资源”之一，不能同时出现在两个用户目录。
2. 用户操作必须落在叶子对象上；分组标题只能提供集合操作，不能伪装成实例。
3. 没有第二个实现或第二个消费者，不新增 registry、manager、facade、lease 或 manifest 字段。
4. 可替换不等于热替换。除 UI 小功能外，默认在下个会话或重启后生效。
5. 所有工具仍必须经过 `ToolPool -> ToolPresentation -> permission/security/trace/abort`，减重不得削弱强制链。
6. 前端不从核心对象推导产品分类；产品分类必须是少量稳定的 UI 数据，而非将底层字段逐项投影。
7. 每一项迁移必须先删除旧入口，再引入新入口；短期兼容层必须写明删除条件。

## 4. 与 VS Code、DSH 的取舍

| 参考 | 采用 | 不照搬 |
|---|---|---|
| VS Code | 用户只管理扩展；工作台、扩展宿主、贡献点与具体视图分离；树形导航只组织用户任务 | 大型 extension host、全面 marketplace、任意扩展直接贡献全部 workbench API |
| DSH | 窄服务接口、明确资源 dispose、一个 MCP 配置对应一个 client 实例、配置与实现分离 | Cordis 全量运行时、所有模块都可 patch、插件树直接成为桌面产品信息架构 |
| 本项目 | 桌面端以“扩展 / 集成 / 资源设置 / 诊断”组织；后端只为真实替换点保留内部 slot | 将每个类、Pane、路由、数据条目都包装为可管理组件 |

## 5. 执行清单

### R0：冻结扩张并建立基线 [P0]

- [x] 停止新增 `CapabilityComponent` 分类、Required binding、第一方 pseudo-package 和用户目录节点。
- [x] 记录当前 `component/package/contribution` 公开 API、生产代码行数、测试数和用户入口数，作为删除基线；详见 [插件化减法基线](./插件化减法基线.md) 和自动生成 JSON。
- [x] 为现有能力逐项标注最终归属：核心、扩展、集成或资源；有争议的项目不得继续迁移。
- [x] 增加 `pluginization-freeze` 门禁：Required manifest、第一方 pseudo-package 和 Pane 注册只能下降，增加必须显式更新基线。

验收：新需求不再以“先进入组件目录”为默认方案；每项都有单一归属。R0 采用截止 2026-08-29 的可复查数据，后续减法允许指标下降。

### R1：先纠正产品信息架构 [P0]

- [x] 将当前“能力组件”用户入口改为“扩展”，只显示实际可安装的 Agent 工具包、模型协议适配和桌面功能扩展。
- [x] 建立独立“集成”入口，MCP Server 直接列为实例；添加/发现为分组动作，实例详情直接提供操作。
- [x] 将非功能的宿主底座、运行时、权限与安全、存储与事件、协议适配移出用户管理列表，改到只读诊断。
- [x] 从主区移除不再对应真实用户任务的通用“组件详情页”；扩展页与集成详情各自使用明确的操作页。

完成记录（2026-08-29）：新增 `/api/components?view=management` 宿主投影，返回 `extensions`、`integrations` 和可恢复扩展；保留完整 `/api/components` 仅供宿主同步/诊断。桌面面板改名为“扩展与集成”，按扩展（桌面端/Agent/服务端）和集成（MCP Server）分组，核心 Required 组件不再渲染；MCP 实例直接打开详情，添加动作仍在集成分组标题上完成。

验收：用户不会在一个列表中同时看到 Host、Pane、工具包和 MCP Server；任一操作不超过一跳。定向组件路由与 Pane 测试通过。

### R2：拆开扩展包、集成实例和资源 [P0]

- [x] 定义最小 `ExtensionManifest`：身份、版本、贡献类型、权限、兼容性和入口；通过 `extensionManifestFromPackage` 从旧 package 声明生成产品扩展声明，扩展声明不再携带 `productClass`、`hostSurface` 等分类字段。
- [x] 定义 `IntegrationRecord`：连接配置引用、信任指纹、启用状态、健康与实例生命周期；MCP Server 通过 `mcpIntegrationRecord` 生成独立实例记录，并提供 `/api/integrations` 脱敏投影。
- [x] 将 Skill、Profile、Provider、Memory 从 package/component 术语中移除，统一归入声明式资源目录与既有服务。`/api/resources/catalog` 现在只返回元数据、状态和指纹，不返回 prompt、Skill 正文、路径或密钥。
- [x] 明确 `UIContribution` 只是扩展挂载点，不自动意味着可安装包，也不自动生成用户行；只有宿主明确登记且管理投影允许的功能扩展才进入桌面列表。

完成记录（2026-08-29）：新增 `src/agent/extension-manifest.ts`、`src/agent/integrations.ts`；资源目录补齐 Provider/Memory；MCP 增加脱敏 IntegrationRecord 投影。旧 `CapabilityComponentManifest` 和 package API 暂留为内部兼容层，R3 再收缩核心替换机制。

验收：从 manifest 可判断“扩展能贡献什么”，从 integration record 可判断“外部实例如何运行”，两者没有相互依赖的分类例外。

### R3：收缩核心替换机制 [P1]

- [x] 将 `CapabilityComponentManager` 的生产替换目录缩至 `AgentEngine`、`ModelRouter`、`SessionStore` 三个明确 slot。
- [x] 将 permission/security/MCP Host 从“面向用户的 Required Component”降为核心服务；保留服务自身健康检查与故障诊断，不提供生产替换事务。
- [x] 删除不再被真实替换使用的非核心 generation/lease/rollback 分支和测试夹具；三个核心 slot 仍保留必需的 generation、lease、rollback。可选工具包的 package recovery 属于安装生命周期，继续由恢复 CLI 管理，不与核心替换事务混用。
- [x] 为三个 slot 使用统一但内部私有的 provider contract，切换默认只在下个 session 或进程重启生效。

完成记录（2026-08-29）：生产 `REQUIRED_COMPONENT_MANIFESTS` 从 8 个收缩为 3 个；权限、安全解析、MCP Host、ToolPresentation 不再注册或绑定到替换目录。旧非核心替换分支与测试夹具已删除；核心 generation/lease/rollback 保留，读取旧 session 时丢弃已移除服务的 provider 引用。可选包恢复仍走独立安装生命周期。

验收：核心替换机制的对象数、事件类型和持久化字段显著减少；普通工具与 UI 不再触及该机制。

### R4：收敛真实扩展生命周期 [P1]

- [x] 将已经存在的第一方 Agent 工具按工具包而非单工具逐项安装，例如 Memory、Planning、Git、Web、File Editing。
- [x] 定义扩展唯一生命周期：install -> validate -> enable -> activate -> dispose -> uninstall；默认不承诺热更新。新增宿主侧 `ExtensionLifecycle` facade，复用 `CapabilityComponentManager` 的依赖、信任和状态投影；激活上下文只提供受控资源登记，dispose 按逆序清理并在失败时进入 `failed`，不会自动回滚为“已安装”。
- [x] 只为有独立代码和独立用户价值的桌面功能提供扩展资格；Search/Git 等可以保留为第一方扩展，布局和 Chat 主体不进入扩展系统。`isExtensionEligible` 对宿主保留面和外部 `server-route`/`model-adapter` fail-closed。
- [x] 扩展 API 只暴露受控的工具、设置、UI 挂载和事件句柄，不暴露 `AgentRuntime`、`ServerContext`、Electron、密钥或安全存储。新增 `createExtensionApi`，所有贡献 ID 按扩展命名空间隔离，设置名拒绝 secret/token/password/key 等敏感字段。

验收：一个扩展停用/卸载不会留下工具、UI、订阅、worker 或子进程；不会为单个按钮创建包。

完成记录（2026-08-29）：R4 第一、二刀完成。生命周期编排集中在 `src/agent/extension-lifecycle.ts`，桌面 HTTP 路由和 `components:recover` CLI 共用该 facade；`extension-manifest.ts` 固化扩展资格，`extension-api.ts` 固化受控贡献面。不加载任意入口脚本、不暴露运行时宿主对象。安装失败和激活失败均 fail-closed，已登记资源全部尝试清理，正常卸载前必须先 dispose。第一方包声明继续由既有 manifest/catalog 提供，未引入第二套安装状态。

## 6. 不做的事

- 不引入 Cordis，不把项目改造成运行时插件树。
- 不实现 arbitrary third-party JavaScript 的即时加载、热卸载或无限嵌套插件。
- 不把核心安全、权限、事件不变量、锁或 Electron/preload 交给普通扩展替换。
- 不把 MCP Server 的每个 tool、Skill 条目、Provider 配置或 Memory 条目做成可安装代码包。
- 不为了“统一”把扩展页、集成页和诊断页强行复用同一套列表和详情组件。

## 7. 完成标准

1. 用户能用一句话区分扩展、集成、资源和诊断。
2. 用户页面不展示底座实现；MCP Server 只在集成中出现，且直接可操作。
3. 后端只有一套真实扩展生命周期和一套独立的集成实例生命周期。
4. 高风险安全链不因减重产生旁路。
5. R0 基线相比，重构范围内生产代码、公开 API 和重复测试净减少，并在每个阶段提交中记录数据。
